# Decisions and assumptions

Recorded so work can keep moving without blocking questions. Newest at the bottom of each phase.

## Phase 1 — Foundation

1. **Stack: Node + Express + TypeScript + Prisma + PostgreSQL, React (Vite) for the web app.**
   The original brief said Next.js; the follow-up said "postgres react node", so the web app is a React SPA and the API is a separate Node service. Backend first; `apps/web` is not started yet. Public pages that need SSR/SEO (landing, catalog) will be handled in the web phase (prerender or a thin SSR layer) — flagged because Lighthouse ≥ 90 is a requirement.
2. **Monorepo with npm workspaces:** `apps/api`, `packages/shared` (design tokens, Tailwind preset, i18n catalogues). No Tailwind installed yet — only the preset exists, ready for `apps/web`.
3. **Prisma pinned to 6.x** (7 and 8-rc change the config and client generation model; not worth the churn). TypeScript pinned to 5.9 for tooling compatibility.
4. **Postgres on host port 5433** to avoid colliding with a locally installed Postgres. A second database `jobprep_test` is created by `docker/init-test-db.sql`. Integration tests refuse to run unless the URL ends in `_test`.
5. **Scope of the two briefs.** The first brief is Rwanda-only; the second adds countries (Kenya, Uganda, Tanzania), M-Pesa and admin roles. The design includes all of those screens, so the schema and seed implement the superset. Rwanda is the only live country.
6. **`CASE_BASED` is a question type** (single-answer, must belong to a `Case`). Single-choice, multiple-select and case-based all sit behind one `QuestionTypeHandler` interface in `src/domain/scoring.ts`.
7. **Multiple-select partial credit:** each correct pick earns `marks / |correct|`, each wrong pick cancels one correct pick, floored at 0. All-or-nothing is the default.
8. **Money is stored as integer minor units** (`priceMinor`, `amountMinor`) with a per-country `currencyExponent` (RWF 0, KES 2). Price `null` = not set → checkout unavailable.
9. **Buying while active extends from the current end date** (no paid days lost). Grants are country-scoped (`AccessGrant.countryCode`); a Rwanda grant never unlocks Kenya. One grant per payment is enforced by a unique constraint, so a duplicate callback cannot double-grant.
10. **Late success after our timeout is honoured** (`EXPIRED` + provider success → `SUCCESSFUL` + grant). The customer was actually charged, so access wins over a neat state machine. Declined / failed / expired copy always says "You were not charged."
11. **Provider modes are seeded as `SANDBOX`, not `LIVE`,** for Rwanda's MTN MoMo and Airtel Money (the design's admin screen shows "Live"). We have no live merchant keys, and showing "Live" would be untrue. An admin flips them after real keys are configured.
12. **Seed content is compact, not the design's 50/45-question exams.** 14 tests, 83 questions: Secondary Mathematics S1–S3 has 20 (design shows 50), the Accountant mock 12 with a 5-question hospital case (design 45 / 10). Time limits are scaled to match. `totalMarks` is computed from the questions, never hardcoded. All answers and arithmetic are checked by integration tests. Real question banks are the owner's content work, reviewed by subject experts.
13. **Languages: tests are seeded English-only.** The design shows "English · Kinyarwanda" on some tests, but seeding machine-written Kinyarwanda risks wrong exam content. The `QuestionTranslation` / `CaseTranslation` tables exist; native-speaking editors add translations, and `MockTest.languages` should be updated when they do. UI catalogues (`packages/shared/src/i18n.ts`) have a small Kinyarwanda/Kiswahili set, falling back to English per key.
14. **Every Rwanda category has a free sample** (acceptance rule), including Government administration, Procurement and Other. Kenya (PREPARING) only has two tests; its go-live checklist should be computed from real data, so it will correctly show missing free samples instead of the design's ✓.
15. **No pass marks anywhere.** `passMarkPercent` + `passMarkSource` exist but are null for every seeded test; a test asserts this.
16. **Dev admins** are seeded (+250788000001 system admin, …02 content editor restricted to RW, …03 support). They sign in by OTP; with `SMS_PROVIDER=console` the code is printed to the server log. Replace before any real deployment. **Superseded by 88:** they are now ordinary accounts with role assignments, and a fourth (`multi.role@jobprep.test`) holds two roles.
17. **`npm run db:reset` uses `prisma migrate reset`,** which Prisma blocks when run by an AI agent without explicit user consent. It works when you run it yourself. Tests use their own `truncateAll` on the `_test` database instead.
18. **Design screenshots not exported.** The design is a private canvas, so I read each artboard's source (copy, tokens, data) directly instead of PNGs. `docs/design/` is empty; add PNGs there if you want pixel comparison in the web phase.

## Phase 2 — Auth and country

19. **Candidate auth is phone + OTP only, session in an httpOnly cookie** (`jp_session`, SameSite=Lax, Secure in production, 30 days). Only an HMAC of the token is stored. Cross-site use from the web app relies on same-site hosting (or a proxy), not on relaxing SameSite.
20. **OTP rules:** 6 digits, 5-minute TTL, 45 s resend cooldown, 5 requests/hour/phone, 5 wrong guesses burn the code, single use, bound to purpose (sign-up vs sign-in). Limits are counted in Postgres so they survive restarts. Codes are never in API responses; the console SMS provider prints them and a test-only endpoint (`/api/test/otp`, forced off in production) reads them. Per-IP limiting is Phase 8.
21. **Account discovery:** sign-up tells you if a number already has an account (409; needed for the "Already have an account? Sign in" UX). Sign-in returns the identical response for unknown numbers and sends no SMS.
22. **Sign-up only in LIVE countries.** Preparing/planned countries get a waiting list (`POST /api/countries/:code/waiting-list`, the design's "Notify me when Kenya opens"). The country is fixed by the phone's dial code + the chosen country and must match.
23. **Changing country** (`GET /api/me/country-change?to=` preview, `POST /api/me/country` with `confirm:true`): target must be LIVE. Grants, attempts and payments stay attached to their own country (access keeps running and returns if the user switches back); the job goal is cleared and language resets to the new country's default.
24. **Guest → account ("Save my result"):** `guestTokens` on sign-up/sign-in, or `POST /api/me/claim-attempts`. Only unowned attempts in the user's own country move; owned attempts are never taken.
25. **Suspended users** cannot sign in and their existing sessions stop working immediately.
26. **Admin sign-in is not built yet** (Phase 7); only the `Session.adminUserId` column and seeded admins exist. *(Moot: see 74 and 88.)*
27. **e2e against the dev DB creates throwaway users** with random +250789xxxxxx numbers; delete them with a normal `db:reset` when you like.

## Phase 3 — Discovery

28. **Public discovery endpoints live under `/api/countries/:code/…`:** `landing`, `mock-tests` (catalog), `mock-tests/:slug` (details), `pricing`, `exam-requests`. They return counts, marks and metadata only — never questions, options, answers or explanations (asserted by tests).
29. **Only LIVE countries are browsable.** Preparing/planned countries return 404 `country_not_available` for every public route, so Kenya's draft tests stay invisible until an admin flips it to live. This is the "Kenya user (country switched to Live in admin first)" acceptance step.
30. **A signed-in user only sees their own country** (403 `country_mismatch` otherwise); guests may browse any live country. Switching country goes through `/api/me/country`.
31. **Search:** every word must match (AND) in title, summary, category, profession or a topic (subject), case-insensitive. User-typed `%`, `_` and `\` are escaped so they match literally. Found by a test: Prisma does not escape LIKE wildcards, so `q=%` used to return everything.
32. **Counts come from published questions,** and the details page's section table and total marks are computed from them — not from the declared `totalMarks`. A draft question changes the numbers immediately.
33. **Exam details access state:** `FREE` (guest can start, no account), `GRANTED` (active same-country grant), or `LOCKED` (shows the database price, payment methods, and a free sample — same profession first, else any free test in the category). A pass mark is returned only when both percent and source are set; negative marking only when configured.
34. **Suggested searches on the home page** are worked out from the live catalog on every request (`activeJobSearches`): published jobs that are still open, soonest closing first, then jobs with no deadline. Closed jobs and the psychometric section are left out. The old `landing.popularSearches:<CC>` setting is no longer read, because a stored list went stale as soon as jobs closed or were removed.
35. **Title sort is byte-order** (Postgres collation), so punctuation sorts differently from a browser's locale sort. Acceptable for English titles; revisit if Kinyarwanda titles need locale-aware ordering.
36. **"Request this exam"** stores a row per request (no dedupe yet); the admin "requested 7 times" alert (Phase 7) will group by normalised query.

## Phase 4 — Exam engine

37. **Guests are identified by a secret `X-Guest-Token` header,** returned once when the attempt starts and kept by the web app in localStorage (`jobprep.guestTokens`, comma-joined in the header). Signed-in users are identified by their session. Anyone else, or a wrong token, gets 404 (not 403), so attempt ids can't be probed.
38. **One running attempt per person per test:** `POST …/mock-tests/:slug/attempts` resumes it (200, `resumed:true`) instead of creating a second; an attempt that ran out while nobody looked is closed first and a fresh one starts.
39. **Autosave is last-change-wins per field,** using the time the candidate made the change (client clock, clamped to never be in the future or before the attempt began). `selectedAt` and `flaggedAt` are stored separately so an old flag change never discards a newer answer. This makes the offline IndexedDB queue safe to replay out of order and in duplicate, and works across two devices. (Replaced the single `clientSeq` column by migration `attempt_answer_field_timestamps`.)
40. **Per-change results** (`saved` / `stale` / `rejected` with a reason) let the client drop acknowledged items from its queue. A batch is one transaction with a row lock on the attempt, so parallel saves and a simultaneous submit are safe.
41. **Late offline sync:** a change is accepted if the time it was made is no later than the deadline + 5 s grace, and the attempt is still running or was *auto*-submitted less than 10 minutes ago. Accepted late changes re-score the attempt and keep the original auto-submit time. This is how "go offline for 2 minutes, answers kept" and "Time is up … nothing you answered was lost" both hold. Trade-off: the client clock is trusted within those bounds. For a practice platform that is fine; a hostile client could back-date up to the deadline, not beyond.
42. **A manual submit closes the attempt for good** (409 `attempt_closed`). Submitting after the deadline is recorded as an automatic submit stamped at the deadline.
43. **Auto-submit happens three ways** so it never depends on the browser: lazily on any request that touches an expired attempt, on save/submit, and by a 30-second background sweeper in the server process (`sweepExpiredAttempts`). If the API is scaled to several instances they can all sweep; the row lock makes it safe.
44. **The attempt state endpoint never returns correct answers or explanations** (asserted by tests); those arrive with the results/review endpoints after submission.

## Phase 5 — Results, review, practice, dashboard

45. **Two cut-offs, as the design implies:** the results screen flags a topic as a "Weak area" under **60%**; the dashboard's "Strong" list is **≥ 70%** and "Needs work" is everything below 70% (the design shows Pedagogy at 67% as "Needs work" but not as a weak area on the results page).
46. **"Incorrect" includes partly-correct multiple-select answers** (they were not fully right). They carry their own `partial` status and marks, so the review can label them "Partly correct".
47. **Comparison and history** use the same person's earlier finished FULL attempts of the same test (user id, or guest token for guests). Practice attempts have no comparison. Results and review are refused while an attempt is running (409 `attempt_in_progress`); an expired attempt is closed on first view.
48. **"Review these first"** = up to 3 wrong answers (not unanswered), weakest topic first, then question number.
49. **Practice sets** (`POST /api/attempts/:id/practice` from results, `POST /api/countries/:code/practice {topicId}` from the dashboard): up to 15 standalone questions (case questions are excluded because they need their passage) from the chosen topics, drawn only from tests the viewer can open — a guest or non-subscriber never gets paid content through practice. Priority: previously wrong/skipped → never seen → answered correctly. Time = 4/3 minute per question rounded up (15 questions → 20 minutes, as in the design). Fewer than 3 available → 409 `not_enough_questions`.
50. **Practice shows the answer after each question** (the dashboard promises "explanations after each one"): `POST /api/attempts/:id/check` works only on PRACTICE attempts, and only for a question already answered (409 `answer_first`), so it can't be used to peek. Real exams never expose answers until submitted.
51. **A practice set's attempt hangs off the test contributing most questions;** its own `questionIds` list is authoritative for scoring, state, results and review (the engine now resolves questions from that list). Its title is generated from its topics.
52. **Explanations on free tests** can be switched off with the existing admin setting `free.showExplanationsOnResults` (default on).
53. **Dashboard** (`GET /api/me/dashboard`): strengths/weaknesses are marks-weighted across everything the user finished in their current country (full tests and practice); the recommendation is the weakest topic that has at least 3 questions the user can open; score history is the last 10 full attempts, oldest first (optionally `?category=`).

## Phase 6 — Payments and access

54. **`PaymentProvider` interface** with MTN MoMo (Collections request-to-pay), Airtel Money and M-Pesa (Daraja STK push) adapters plus a `fake` provider. In `PAYMENT_PROVIDER_MODE=fake` every method is served by the fake provider; in sandbox/live only the real webhooks exist. **The three real adapters are unit-tested against a mocked `fetch` (request shape, status mapping, callback auth) but have never run against the operators' sandboxes: that needs your developer keys.**
55. **One idempotent core (`applySignal`)** takes every outcome, from webhook, poll or timeout: it locks the payment row, records the event with a dedupe key (`ON CONFLICT DO NOTHING`), runs the state machine, and creates the grant. A duplicate callback, a replayed poll, a webhook racing the poller, or two parallel deliveries grant exactly once (the unique `paymentId` on the grant is the last guard).
56. **Late success is honoured:** a success after our 3-minute timeout moves EXPIRED → SUCCESSFUL and grants access (the payer was charged). Declined and failed are final. Before expiring a payment we poll the operator once more, so an approval at the deadline isn't lost. A background sweeper also settles lost callbacks and keeps checking recently expired payments for an hour.
57. **Callbacks are authenticated and fail closed:** the fake provider signs with HMAC-SHA256; MTN, Airtel and M-Pesa callbacks carry a shared secret in the callback URL (`?token=`), compared in constant time, and are rejected if no secret is configured. Unknown payment references get 200 and are ignored. The callback secrets must be set before going live.
58. **Never a PIN:** the payer only types their phone number; the API ignores any extra fields and tests assert nothing PIN-like is stored. The pending screen tells the payer to approve on their own phone.
59. **Price is read on the server and snapshotted** on the payment (`amountMinor`); no price set → 409 `checkout_unavailable`. A payment is only created for a configured, non-disabled method of the user's country, with a phone number of that country.
60. **"Send again" / "Use a different number"** close the old request (as expired, kept open to a late approval) and send a new one; if the old one was approved meanwhile nothing new is sent. Trade-off: if the payer approves both prompts they pay twice and both grants stack, which is correct for what they paid.
61. **Renewals chain:** buying while active creates a second grant starting where coverage ends. Access end dates shown anywhere are the end of *continuous coverage* (`coveredUntil`), not the end of the first grant. (Found by a test: "days left" showed 20 instead of 50 after a second purchase.)
62. **SMS receipt** is sent after the commit and a failing gateway never undoes a payment or access. **Its wording is mine; there is no design for it** (see docs/MISSING_DESIGNS.md).
63. **Test-only simulator** (`POST /api/test/payments/:id/simulate`: success, decline, fail, duplicate, timeout) exists only with `ENABLE_TEST_ENDPOINTS` and the fake provider, both refused in production.

## Phase 8 (backend part) — Hardening

64. **Per-IP rate limits** (fixed window, in memory) on login-code requests (10/min), sign-up and sign-in verify (20/min), creating or resending payments (10/min), payment checks (30/min), exam requests and the waiting list (10/hour, one shared counter), starting attempts and practice sets (30/min), webhooks (600/min), and everything else (1,200/min). Answers are `429 rate_limited` with `Retry-After`. **Default: on in production, off in development and tests** (the e2e suites sign up dozens of users from one IP); set `RATE_LIMIT_ENABLED` to force either way. The limiter is per API instance; run several instances and a shared store (Redis) is needed. The per-phone OTP limits live in the database and always apply.
65. **Production refuses to start with unsafe configuration**, and lists every problem at once: fake payments, console SMS, a session secret under 32 characters or containing "change-me", non-https `PUBLIC_API_URL` / `WEB_ORIGIN`, and any missing or short (< 16) MTN / Airtel / M-Pesa callback secret. Test endpoints are forced off.
66. **Still to do in hardening, and needs the web app or your input:** the keyboard-only and accessibility pass over the exam UI, Lighthouse on the final build, authorisation checks on admin routes (admin is blocked on design), CSP headers for the web host, error reporting and request logging, backups, and a shared rate-limit store if scaled out.

## Batch 1 designs — decisions taken when told "build all"

Where the designs and the backend disagreed, the owner said "build all" without choosing, so these are the **defaults I took (the recommendations)**. Each can be reversed; the owner should confirm them.

67. **Sign-in copy follows the backend, not the artboard.** Code lifetime, resend wait and tries left now come from the API (`expiresInSeconds` 300, `cooldownSeconds` 45, `triesLeft` on a wrong code), so screens never hard-code them. The artboard's "10 minutes" and "wait 15 minutes" are wrong for this backend: after 5 wrong tries the code is dead and the user requests a new one (45 s resend wait, at most 5 codes an hour). `code_expired` is now a separate error from `invalid_code` (it can't leak whether an account exists: unknown numbers get a silent code row too).
68. **"Choose N" is real.** A multiple-select question accepts at most N picks (`payload.choose`, default = the number of correct options); the exam state returns `choose`, and the server rejects more with `too_many_choices`. Note this shows the candidate how many answers are correct, as the design does. Scoring stays per question: all-or-nothing, or partial credit (equal share per correct pick, each wrong pick cancels one, never below 0); the seeded multiple-select question uses partial credit.
69. **Practice sets are untimed** (as the Practice artboard draws): `timer.untimed = true`, no low-time state, no `minutes`; the attempt only keeps a 12-hour safety limit so abandoned ones are closed. The dashboard artboard's "15 questions · 20 min" line therefore no longer applies to practice and must be corrected by the designer.
70. **C29 phone navigation is the standard** (Home, Tests, Progress, Account); the older tab bar in `DashboardPhone` is superseded.
71. **No operator-prefix check on payment numbers.** The "number on another network" state in `CheckoutStates` is shown only if the operator itself rejects the number; the backend does not guess operators from prefixes (number portability makes that unreliable).
72. **API additions for the new screens:** dashboard `startHere`, `suggestedTests`, `pendingPayment`; access `endingSoon` (3 days or fewer), `expired.endedAt`; checkout `currentAccess` and `newAccessEndsAt` (buying while active adds days after the current end); details `inProgress`; `X-Request-Id` on every response and `requestId` in every error body (the error page's "Reference").
73. **Still open for the owner:** the waiting-list opt-out wording, the real values for [PRICE], [SUPPORT PHONE] and the maintenance [TIME].

## Phase 7 — Admin (backend complete; screens only where a design exists)

74. **Admin sign-in is phone + code, with its own cookie** (`jp_admin`, SameSite=Strict, 12 hours). The code request answers the same for a number that is not an admin and sends nothing to it. Deactivating an admin or changing their role ends their open sessions at once. Admin and candidate sessions never mix. **Superseded by 88:** there is no admin cookie, admin sign-in endpoint or admin-only session; admins sign in like everyone else, and the 12 hours became a freshness rule on the normal session.
75. **Permissions come from the admin's role** (System admin: everything; Content editor: exams, questions, reports; Support: view users, resend login codes, view and check payments). Every route names its permission; a test calls every route as every role (153 cases) and a second test shows the blocked actions change nothing. **Amended by 88:** an account's effective permissions are the union over all its active roles.
76. **Country restriction:** a restricted admin sees only their countries across the overview, users, payments, exams, reports and categories. Anything outside is a **404**, not a 403, so other countries cannot be probed. **Amended by 88:** the scope belongs to each role assignment, and the effective scope of an account is all countries if any active role is unscoped, else the union.
77. **Reasons and the audit log:** granting or extending access, suspending or un-suspending, manual payment grants, price changes, status changes, payment-method changes and team changes all require a reason (checked inside `writeAudit`, which throws `reason_required`). The audit entry is written **in the same database transaction** as the change, so the log can never disagree with what happened. A test scans the route source to prove every state-changing admin route writes an audit entry.
78. **Manual payment grant:** needs the operator's transaction id and a reason; allowed only for a payment that is pending, expired or failed; **never for a declined payment**; one operator transaction id can only pay once; recorded as a MANUAL grant with who, why and the transaction id. A real callback arriving later cannot grant a second time.
79. **"Stuck" payment** = pending longer than the setting `payments.stuckAfterMinutes` (default 10). It drives the overview alert, the "stuck" filter and the manual-grant action.
80. **Going live:** a country needs the checklist (price set, a payment method set to LIVE, a free sample in every category, legal review marked) or an explicit **forced** go-live with a reason, which is logged as a separate "forced live" action. Every status change needs a reason. Price changes apply to **new payments only**: open payments keep the price shown to the payer and active access is never shortened.
81. **Content rules:** edits reach candidates at once and bump the question's version; drafts and imported questions are invisible to candidates until published; "delete" archives (history is kept); a test cannot be published without a published question; an official pass mark needs its source; topics, sections, cases and categories cannot be deleted while in use; CSV import is all-or-nothing by default, or valid rows only on request, always as drafts.
82. **Deliberately not built (no design, or no data):** "View as candidate", "Export for accounting", an admin-side "support requests" alert (there is no support-request feature), a switch for "free samples without an account" (that is a product rule, shown but not changeable), duplicate test, per-language question editing screens (translations exist in the data model; the editor API does not write them yet).
83. **Added without a screen:** a candidate endpoint to report a question (`POST /api/attempts/:id/reports`), which feeds the admin queue. No candidate screen for it is designed.
84. **Attempt numbers ("attempt 2")** are now stable when two attempts finish at the same instant (found by a test; fixed in the admin view and the candidate dashboard).
85. **Test infrastructure:** when several people or agents run the API tests at once they must use different test databases (`TEST_DATABASE_URL`, name ending `_test`), because each test file truncates and re-seeds its database. `jobprep_admin_test` was created for admin work.

## pawaPay as the live payment provider

86. **pawaPay (v2 API) is the live provider** (`apps/api/src/payments/pawapay.ts`). **It has never been run against pawaPay**, not even its sandbox; it is unit-tested against a mocked `fetch` only, from the API facts of the owner's other integration. Superseding the live part of 54 and 57: the MTN, Airtel and M-Pesa adapters stay in the code with their tests, but production no longer requires their callback secrets; it requires `PAWAPAY_API_TOKEN` (non-empty) and `PAWAPAY_CALLBACK_SECRET` (16+ characters).
    - **No database change.** pawaPay is an aggregator, so it serves the existing methods (`MTN_MOMO`, `AIRTEL_MONEY`, `MPESA`); `Payment.provider` keeps those values and the Prisma enum is untouched. Its own code is `PAWAPAY` (type `AdapterCode`). The payer's choice in the checkout does not decide the operator: `POST /v2/predict-provider` on the phone number does (so a wrong choice still works, consistent with 71). The provider id is the deposit id, a UUID we generate, and is stored as `providerReference`.
    - **Selection:** in `sandbox`/`live` mode, pawaPay serves every method when `PAWAPAY_API_TOKEN` is set, and then only its webhook exists (`/api/payments/webhooks/pawapay`; the old slugs answer 404). With the token empty the direct adapters are used as before. Production forces the token to be set, so it always uses pawaPay.
    - **Callback authentication:** pawaPay callbacks are not signed, so it is the `?token=` shared secret (`requireTokenSecret`, constant-time, fail closed if the secret is empty). The deposit callback URL is configured in the pawaPay dashboard, not per request, so the dashboard URL **must** be `<PUBLIC_API_URL>/api/payments/webhooks/pawapay?token=<PAWAPAY_CALLBACK_SECRET>`; the adapter does not send a callback URL. The secret is also in the URL, so it ends up in access logs of anything in front of the API: keep request logging of query strings off at the gateway.
    - **A callback success is confirmed before it is trusted:** `handleCallback` now has two optional adapter flags, `confirmSuccessByStatus` and `aggregator`. For pawaPay, a `COMPLETED` callback only settles the payment if `GET /v2/deposits/{id}` also says `COMPLETED`; if the lookup fails the webhook answers 5xx so pawaPay retries; if it disagrees nothing changes and the poller or sweeper settles it. So a leaked secret can forge at most a status check, never access. Failures and other statuses in callbacks are applied as sent (they only close a pending payment). The extra call is one request per successful payment.
    - **Status mapping (my judgment, unverified against live traffic):** `COMPLETED` → SUCCESSFUL. `ACCEPTED`, `PROCESSING`, `IN_RECONCILIATION`, `DUPLICATE_IGNORED`, anything unknown, and a deposit not found (404 / `NOT_FOUND`) → PENDING. `FAILED` → EXPIRED when the failure code is a timeout code or the failure message says timed out / timeout / expired (the payer never answered; a late approval is still honoured); → DECLINED for `PAYMENT_NOT_APPROVED`, `INSUFFICIENT_BALANCE`, `WRONG_PIN`, `INVALID_PIN`, `PAYER_REJECTED` (final: the payer said no or cannot pay); → FAILED for every other code (`PAYER_NOT_FOUND`, `UNSPECIFIED_FAILURE`, ...). Declined and failed are final (56) and a manual grant is never allowed for declined (78), so **if pawaPay reports a timeout under `PAYMENT_NOT_APPROVED` without saying so in the message, it will show as declined**: check real failure codes in the sandbox and adjust the sets at the top of `pawapay.ts`.
    - **Deposit rejected** (`REJECTED`, with its failure code) is an error: the payment is closed as failed with `provider_error` and the payer sees "provider unavailable"; nothing was sent to them. `DUPLICATE_IGNORED` on creating is treated as accepted (the id already exists). Amounts are sent as a major-unit string (`"2000"`; `"150.5"` for 15050 KES minor). The token and the callback secret are never logged or put in error messages; no PIN is ever sent.
    - **Needs the owner:** which countries and operators are enabled on the pawaPay account (a country or operator not enabled there makes `predict-provider` or the deposit fail), the dashboard callback URL above, the sandbox token for a first test, and whether a payment's currency matches what pawaPay allows per operator.

87. **Accounts are identified by email, not phone (owner decision, no SMS).** *(The "one-time codes sign you in" part is superseded by 89: sign-in is email + password or Google.)* `User.email`, `AdminUser.email`, `OtpCode.email`, waiting list and exam requests use lower-cased email; one-time codes (**no longer a sign-in method: see 89**, now only to verify a new account) and payment receipts are emailed (`EmailProvider`: console for dev/test, SMTP via `MAIL_*` in production; production refuses console). Phone numbers exist only as the mobile-money payer number (`Payment.msisdn`); checkout pre-fills the number of the user's last payment. Sign-up needs a country (explicit `countryCode`, previously inferred from the dial code). Migration `email_identity` renames the columns (and drops pending codes). The first production admin is made with `npm run admin:create`, not the seed. (`AdminUser.email` no longer exists: see 88.) Every designed screen with a phone field or SMS copy was swapped in place and listed in MISSING_DESIGNS for the designer.

88. **One account, many roles: there is one backend and one frontend, and admin people are not a separate account type (owner decision).** An admin is a normal `User` (identified by email, signs in with the normal emailed code, normal `jp_session` cookie) who holds one or more active `UserRole` assignments. **Supersedes** the separate admin accounts and cookie of 74 (admin sign-in endpoints, `jp_admin`, SameSite=Strict, admin-only sessions), the seeded-admin wording of 16, the "not built yet" note of 26, and the `AdminUser.email` part of 87; amends 75 (permissions) and 76 (country scope); 77 to 85 are unchanged (audit actors and grant/resolver ids now point at `User`).
    - **Schema** (migration `one_account_many_roles`, data-preserving): new `UserRole { userId, roleId, countryScope[] (empty = all countries), active }`, unique per `(userId, roleId)`; `Role` stays (permissions are data); `AdminUser` and `Session.adminUserId` are gone (`Session.userId` is now required); `AccessGrant.grantedById`, `QuestionReport.resolvedById` and `AuditLog.actorId` point at `User`; the `ADMIN_SIGN_IN` code purpose is removed (pending admin codes and admin-only sessions are deleted by the migration). Each old admin row became (or was matched by email to) a `User` in Rwanda, English, with a `UserRole` carrying its scope and active flag, and every foreign key was re-pointed through a temporary mapping table.
    - **Who may use `/api/admin/*`:** a valid normal session, an ACTIVE account (suspending signs the person out everywhere), at least one active role, and a session created at most **12 hours** ago (`ADMIN_SESSION_HOURS`). Otherwise: 401 `admin_sign_in_required` (no session), 401 `admin_session_stale` (signed in, but over 12 hours ago: the UI asks them to sign in again; the normal session itself still lasts 30 days for candidate use), 403 `admin_forbidden` (no active role, or the role lacks the permission). The role assignments are read on **every request**, so adding, changing or removing a role applies on the very next request with no sign-out needed. A role-less account with an old session gets the 403, not the stale 401.
    - **Several roles:** effective permissions are the **union** over active roles. Effective country scope is **all countries if any active role is unscoped, otherwise the union of the scopes.** This is a deliberate simplification: scope is not tracked per permission, so a content editor scoped to Rwanda who also holds an unscoped Support role can edit Kenya content too (everything is all-countries). If that is not wanted, do not give that person an unscoped second role; a per-permission scope would need a schema change. Out of scope is still a 404.
    - **CSRF:** the session cookie is SameSite=Lax, so for every non-GET/HEAD/OPTIONS request under `/api/admin`, an `Origin` header, if present, must equal the origin of `WEB_ORIGIN` (else 403 `bad_origin`). A request with no `Origin` (curl, tests, server-to-server) is allowed. Behind a proxy, `WEB_ORIGIN` must therefore be exactly the origin the browser shows (scheme, host, port).
    - **Team (Settings, Admin team):** `GET /api/admin/team` lists accounts holding at least one assignment, including inactive ones, with `roles[]` and the legacy single-valued `role`/`roleLabel`/`countryScope` (first active role). `POST /api/admin/team` adds the role to an existing account with that email (409 `already_has_role` if already active; an inactive one is reactivated with the new scope; the existing name is kept) or creates a new account (Rwanda, English). **Inviting never sends an email:** the person signs in with that address. `PATCH /api/admin/team/:id` changes one assignment: `role` says which (default the first active one), `newRole` moves it to another role, `countryScope`, `active:false` removes it (and `true` restores it), `name` renames the account. Guardrails kept: reasons required, audit in the same transaction, a system admin cannot change or deactivate or suspend themselves, the last active system admin cannot be removed, changed or suspended (409 `last_system_admin`), and a system admin has no country scope. Admins appear in the normal users list with `roles`; suspending an admin works like suspending anyone.
    - **First admin:** `npm run admin:create` finds or creates the normal account for that email and ensures an active, all-countries SYSTEM_ADMIN assignment; an existing candidate keeps their history and other roles.
    - **Not done / consequences:** there is no longer an `admin.sign_in` audit entry (sign-in is the normal one, not audited). Role changes are not an "admin session" event any more, so nothing is deleted from `Session`. An admin who is also a candidate shares one country (`User.countryCode`) for their candidate side.

89. **Sign-in is email + password, plus "Continue with Google" (owner decision: the same method as the owner's other product, Mwalimu Tools).** The emailed 6-digit code is no longer a sign-in method: it is used ONCE, to verify a new account's email. **Supersedes** the emailed-code sign-in of 87 (and the code parts of 19, 20, 21, 67, 74, 88: no purpose-based `/otp/request`, no code `/sign-in`, no "code for sign-in"). Everything about the code itself (6 digits, hashed, single use, 5 wrong tries, 45 s wait, 5 per hour, per email, in Postgres, silent rows for unknown addresses so nothing leaks) is unchanged; its lifetime is now 10 minutes (`OTP_TTL_SECONDS` 600) and the purpose enum is just `VERIFY_EMAIL`.
    - **Schema** (migration `password_sign_in`, data-preserving, hand-written): `User` gains `passwordHash`, `emailVerifiedAt`, `googleId` (unique), `failedSignIns`, `signInLockedUntil`, `countryConfirmedAt`, `level`, `subject`, `examDate` (date), `onboardedAt`; new table `PasswordReset` (hashed token, 1 hour, single use); `OtpPurpose` recreated as `VERIFY_EMAIL` (pending codes deleted). Existing people: `emailVerifiedAt`, `countryConfirmedAt` and `onboardedAt` = `createdAt` (they proved the address by code and are not sent through setup), no password (they use "Forgot password" once).
    - **Passwords:** `node:crypto` scrypt (N=16384, r=8, p=1, random 16-byte salt) stored as `scrypt$N$r$p$salt$hash`, read back with the stored cost, constant-time compare, NFKC-normalised; 8 to 128 characters and nothing else (no composition rules, no common-password list: trade-off, kept simple). A dummy hash is computed when the email is unknown or the account has no password, so timing does not reveal accounts. Hashes are never logged or returned.
    - **Flows:** *Sign-up* creates an UNVERIFIED account (country: a given live country, else Rwanda; the person picks it in setup step 1) and emails the code; no session. If the address is an unverified account, the newest sign-up overwrites name and password and sends a new code (a verified one is 409 `account_exists`); known trade-off: someone who knows an unverified address can overwrite the password in the window before its owner verifies, and the owner then verifies an account with the other person's password. Mitigations: the 45 s / 5 per hour limits, a real owner can reset the password, and Google linking drops the password of an unverified account. *Verify-email* verifies, signs in (30-day cookie), claims guest attempts; an already verified account never signs in with a code. *Resend* answers the same for unverified, verified and unknown addresses (same limits for all). *Sign-in* errors: `invalid_credentials` (identical for unknown, wrong password, no password), `email_not_verified` (right password; no code is sent automatically), `account_suspended`, `too_many_attempts` (429 + `retryAfterSeconds`). *Remember me:* 30-day persistent cookie; otherwise a browser-session cookie and a 24-hour server expiry. The admin 12-hour rule is unchanged (from the session's creation time).
    - **Lockout:** 5 wrong passwords in a row for an EXISTING account (also one without a password, so the lock looks the same) lock it for 15 minutes; the lock is checked before the password; the 5th wrong try already answers 429; the counter resets on success, when the lock is applied, and on a password reset. Known leak, accepted: an unknown address is never locked, so someone who tries 5 times can tell the two apart. The per-IP limit (20 sign-ins a minute) is the other guard; closing this fully would need a counter per address string.
    - **Forgot / reset:** always `{ ok: true }`; the 45 s wait and 5 per hour (counted from the account's reset rows) only decide whether an email is sent, never the answer. The send is not awaited, so SMTP latency cannot reveal an account. Accounts that are suspended get nothing. A new link marks earlier unused ones used (not deleted, so they still count towards the cap). Resetting sets the password, verifies the email, clears the lock, deletes ALL the person's sessions and does not sign them in. Admin `POST /api/admin/users/:id/send-password-reset` (permission `otp:resend`, audit `password.reset_sent`) replaces `send-login-code`; it keeps the usual resend limits (429 `otp_cooldown` / `otp_hourly_limit`) and refuses suspended people.
    - **Google:** server-side authorization-code flow with no new dependency. `state` is an HMAC-signed payload (nonce, next, country, 10 minute expiry) and the nonce is also in an httpOnly `jp_google_state` cookie scoped to `/api/auth/google`; both must agree. The id_token is read from Google's token response over TLS (not signature-verified, as agreed); issuer, audience, expiry and `email_verified` are checked. Match by `googleId`, else by email (linking: Google has verified the address; if the existing account was unverified it becomes verified and its password is dropped), else create a verified account without a password. An address already tied to another Google account is refused. Every failure, including a suspended person, is a redirect to `/sign-in?error=google_failed`; `next` is only kept when it is a same-site path. Guest attempts are not claimed in this flow (the redirect cannot carry the tokens): the web app calls `POST /api/me/claim-attempts` after the callback. Never run against Google; unit-tested with a mocked fetch. Not required in production, but a half-configured pair is refused.
    - **Setup (onboarding):** `PATCH /api/me/onboarding` (country, goal category, level, subject, exam date, finish, skip). `user.onboarding.nextStep`: `country` until the country is confirmed; then, until setup is finished or skipped, `category` (no goal) and `goal` (level or subject missing); else null. Changing country (here and in `POST /api/me/country`, one shared function) clears goal, level and subject AND reopens setup (`onboardedAt` cleared), as the Change-country design says. Old accounts have `onboardedAt` set by the migration, so they are never asked for a goal. `finish` and `skip` need a confirmed country and a goal (409 `onboarding_incomplete`).
    - **Seed and first admin:** dev admins get `DEV_PASSWORD` (`Password123!`, exported from `prisma/seed-lib.ts`), verified and set up; production seeds no passwords. `admin:create` takes an optional third argument (password, new accounts only); otherwise the first admin uses "Forgot password" (needs email).
    - **Rate limits (per IP, production default-on):** sign-up 10/min, sign-in 20/min, verify-email 20/min, resend 10/min, forgot-password 10/min, reset-password 10/min.

## Missing designs: API built without designs (backend pass)

The owner asked for everything in `docs/MISSING_DESIGNS.md` to be built in the existing style with no new designs. Contract: `docs/API_ADDITIONS.md`; item by item: `docs/missing-built-backend.md`. Choices that are not obvious:

90. **No new permission strings.** The new admin routes reuse `exams:*`, `reports:resolve`, `countries:*`, `payments:read`, `users:read`, `settings:write`, `audit:read`. Roles are rows in the database, so a new permission string would have needed a data update on every deployed database. Consequences: demand lists (exam requests) follow `exams:read/write` so Content editors can plan tests from them; the waiting list follows `countries:*` (System admin only); Support can read payments, export them (accounting CSV) and "view as candidate" (`users:read`). If Support should not export, a `payments:export` permission plus a data update is the way.
91. **Exam requests are de-duplicated by address, never by anonymity.** The same email asking for the same search (case and spacing ignored, `normalizedQuery`) is stored once; a request without an address is always stored, because each one is another person and the count is the demand signal. Requests have a status (`OPEN` / `DONE`); "Mark done" closes every open request for that search and can email the requesters (at most 500 per click; one email, saying nothing else). The overview alert ignores done requests.
92. **The waiting list answers "already on the list" with 200** (first time 201), keeps the optional `interest`, and can be emailed once the country is LIVE (`notifiedAt`, a failing mail server leaves the person un-notified so the next click retries). A signed-in person may leave the address out.
93. **Settings-driven content, never typed into the web app:** support contact per country (`support.contact:<CC>`, env fallback `SUPPORT_*`, dev seed placeholders flagged `placeholder: true`), legal pages (placeholder text in code, flagged; an admin's text is stored as `legal.page:<slug>:<CC or *>` and replaces it), and the maintenance switch (`system.maintenance`, shown by `GET /api/status`). Maintenance is a flag for the web app to show its page; the API itself does not block requests.
94. **Translations are an overlay, not a second test.** `?lang=rw|sw` on the attempt state and review replaces stem, options, explanation (and case title, passage, tables, notes) where a translation exists and leaves English elsewhere; the answer says how many questions were translated. The first language of a test is its source; only the others take translations. "Complete" = stem, explanation and every option filled; partial work can be saved. Saving bumps the question's `version`. Correctness never lives in a translation, so it cannot leak an answer.
95. **Publish checklist:** blocking = at least one published question and a title; warnings (do not block) = a free sample exists in the category, instructions, translations complete. A paid test with no free sample in its category still publishes, with a warning: blocking would stop the very first test of a new category from ever being published, and the go-live checklist already enforces "a free sample in every category" per country. An ARCHIVED test must be restored (to draft) before it can be published; unpublish needs a reason (it hides content from candidates), keeps attempts in progress running and keeps history; duplicate copies the test as a draft with its sections, case studies, non-archived questions and translations.
96. **Reports:** dismissing needs a reason (400 `reason_required`), resolving may have one; it is stored on the report (`resolutionNote`) and in the audit row. The grouped view (`?group=question`) counts reports per question; "close all of a question" is one action with one audit row.
97. **"Recommended next" respects level and subject.** The free-text chip values are matched against the test title, profession and topic names; the code in brackets of a level ("S4–S6") ranks above the word ("Secondary"); tests already completed rank last; nothing is hidden. Dashboard `startHere`, `suggestedTests` and `GET /me/recommended-tests` share one function (`services/recommend.ts`). This fixes the bug where level and subject were ignored.
98. **Practice sets are not attempts of their test.** Exam details count and list FULL attempts only, with `attemptStats` (count, best, last): a practice set anchored to a test no longer appears as "last attempt" or inflates the count or the best score (API_GAPS 13).
99. **Account changes:** `POST /me/password` needs the current password (none for a Google-only account), signs the other devices out, and wrong current passwords count towards the same 5-in-a-row lock as sign-in. Changing the email is two steps with the existing code machinery: a code to the NEW address, then the code (the address becomes the identity and is marked verified). A taken address is 409 `email_taken` (the person is signed in, so this is not an enumeration risk beyond what sign-up already allows).
100. **"View as candidate" is data, not impersonation.** `GET /admin/users/:id/candidate-view` returns the dashboard, attempts and payments of the person, read only; no session switch, so nothing can be changed by mistake, and every look-up is audited (`user.view_as_candidate`). The web app draws its read-only banner over that data.
101. **Exports:** CSV with a byte-order mark (Excel reads accents), spreadsheet formulas neutralised (a leading `= + - @` gets a quote), the payer's number masked to its last 4 digits, no secrets, scoped to the admin's countries, and every export is audited. Accounting dates paid payments by confirmation time and the others by creation time.
102. **"Save my result" says what happened** (`saved`, `already_saved`, `nothing_to_save`, with counts per reason and the attempt ids) and reopening a finished attempt says whether a new one may start (`reopen.canStartNew`).
103. **Not built:** the Overview "support requests" count (there is no support-request feature or data), reordering topics (they have no order; sorted by name), "Not listed? tell us your country" capture (no design, no screen), IP geolocation for "Detected from your connection" (not wanted; the design should drop the line), a per-permission country scope (see 88).
104. **Test infrastructure:** `hookTimeout` is 60 s (the default 10 s made `beforeAll` truncate-and-seed time out when the machine was busy, which skipped whole files).
